# Helpdesk — AI-Powered Ticket Management System

Support emails become tickets; AI classifies them, summarizes them and drafts replies from a knowledge base; agents review and respond.

Planning docs (read before starting a feature):
- `project-scope.md`: problem, features, ticket statuses/categories, roles
- `tech-stack.md`: chosen stack and rationale (database-session auth, AI models)
- `implementation-plan.md`: phased task list; tick off tasks (`- [x]`) as they are completed

## Documentation lookup

Always use the **Context7 MCP server** (`resolve-library-id` → `query-docs`) to fetch up-to-date documentation before writing or changing code that uses a library, framework, SDK or CLI (Express, React, Vite, Prisma, Better Auth, pg-boss, TanStack, Tailwind, shadcn/ui, Zod, Anthropic SDK, etc.). Do not rely on memory for APIs or configuration; these versions are newer than most training data. Context7 is configured in `.mcp.json`.

## Project structure

npm workspaces monorepo:

```
shared/   @helpdesk/shared: types/schemas shared by client and server; compiles to dist/
server/   @helpdesk/server: Express 5 API (src/app.ts = routes, src/index.ts = startup)
client/   @helpdesk/client: React 19 + Vite 8 SPA; proxies /api to the server
e2e/      Playwright end-to-end tests and their setup (config in playwright.config.ts at the root)
```

## Commands

Run from the repo root:

- `npm run dev`: builds `shared`, then runs shared watcher + server (tsx watch, port 3000) + client (Vite, port 5173 or next free)
- `npm run typecheck`: type-check all packages (including `e2e/`)
- `npm run build`: build shared → server → client
- `npm start`: run the built server
- `npm test`: build `shared`, then run the Vitest unit tests for all packages (`npm run test:watch` for watch mode; `npx vitest run --project server` for one package)
- `npm run test:e2e`: build `shared`, then run the Playwright tests (`npm run test:e2e:ui` for UI mode; extra args pass through, e.g. `npm run test:e2e -- e2e/login.spec.ts`)

Install packages into a workspace with `npm install <pkg> -w server` (or `-w client`, `-w shared`).

## Unit testing (Vitest)

- `vitest.config.mts` at the root lists each workspace as a project; each has its own `vitest.config.ts`. Tests sit next to the code as `src/**/*.test.ts(x)`.
- Build tsconfigs (`shared/tsconfig.json`, `server/tsconfig.json`) exclude test files so they never reach `dist/`; `tsconfig.test.json` in each type-checks everything, and `npm run typecheck` uses it.
- Server tests use `supertest` against `app` with `../auth.js` and `../db.js` replaced by `vi.mock` (see `server/src/routes/users.test.ts`), so they need no database or env file. Use the e2e suite for real database and Better Auth behaviour.
- Client tests run in jsdom with Testing Library (`client/src/test/setup.ts` loads the jest-dom matchers). Stub `fetch` with `vi.stubGlobal` and wrap components that use TanStack Query in a fresh `QueryClientProvider`.

## End-to-end testing (Playwright)

- Tests live in `e2e/` as `*.spec.ts` and run in Chromium only. Import `test`/`expect` from `@playwright/test`; use relative URLs (`page.goto('/login')`), since `baseURL` is set.
- Tests use a separate database, never the dev one. Settings come from `server/.env.test` (git-ignored; template in `server/.env.test.example`): its own `DATABASE_URL` (database `helpdesk_test`), `BETTER_AUTH_SECRET`, ports and test admin credentials. `e2e/test-env.ts` loads it and refuses to run unless the database name ends in `_test`.
- `playwright.config.ts` starts two servers of its own, so tests can run while `npm run dev` is up:
  - API on port 3001 (`server/`): runs `prisma migrate deploy` against the test database (creating it if needed), then starts the server with `serverEnv` from `e2e/test-env.ts` and no `--env-file`, so the app never reads `server/.env`. It does not run `prisma generate` (that would restart a running dev server); the client is generated by `npm run dev`, `typecheck` or `build`, or `npm run db:generate -w server` after a fresh clone or schema change.
  - Environment: Playwright starts servers from the shell's environment and layers `serverEnv` on top, so `.env.test` values win but other exported variables leak through. `serverEnv` blanks optional server settings (`TRUST_PROXY`); add any new optional server variable there (e.g. AI provider keys). The Prisma CLI also loads `server/.env` via `prisma.config.ts` but doesn't override set variables, which is why `DATABASE_URL` must stay required in `.env.test`.
  - `e2e/test-env.ts` also checks that `BETTER_AUTH_URL` matches `PORT` and that `TRUSTED_ORIGINS` includes `http://localhost:5174`.
  - Client on port 5174: Vite with `API_PROXY_TARGET=http://localhost:3001` (read by `client/vite.config.ts`; defaults to port 3000 for dev).
- Each run starts from a clean database: `e2e/global-setup.ts` (which runs after the servers are up) truncates every table except `_prisma_migrations`, then runs `server/src/seed.ts` to create the test admin.
- Tests run one at a time (`workers: 1`, `fullyParallel: false`) because they share one database. Create the data a test needs inside the test; don't rely on data left by another test.
- Sign in as the seeded admin with `testAdmin` (`email`, `password`, `name`) from `e2e/test-env.ts`; never hard-code credentials.
- Sign-in is rate-limited to 5 attempts per minute per IP in tests too, and CI retries repeat sign-ins, so specs that sign in set `test.describe.configure({ retries: 0 })`. Sign in once in a setup project, save `storageState` to `e2e/.auth/` (git-ignored) and reuse it; only the login tests should sign in through the form. The `setup` project (`e2e/auth.setup.ts`) signs in the admin through the API and saves `adminStorageState` (from `e2e/test-env.ts`); specs opt in with `test.use({ storageState: adminStorageState })`. Sign-in budget per run: setup 1 + login spec 2 + users spec 2 (new agent, then the same agent after deletion) = 5, the per-minute limit, so new sign-ins need the budget rearranged.
- Reports and traces go to `playwright-report/` and `test-results/` (git-ignored). On CI: 2 retries, `test.only` is rejected, and traces are kept on the first retry.
- The Chromium browser is installed per machine: run `npx playwright install chromium` after a fresh clone or a Playwright upgrade.

## Conventions

- TypeScript everywhere; strict mode. Server and shared use `nodenext` modules, so relative imports need `.js` extensions (`import { app } from './app.js'`).
- All API routes live under `/api` and are defined in `server/src/app.ts` (or routers it mounts), never in `index.ts`, so the app can be tested without listening on a port.
- Types used by both client and server go in `shared/src` and are imported from `@helpdesk/shared`.
- `shared` must be built before server/client can see changes (`npm run dev` watches it automatically).
- Secrets go in `server/.env` (git-ignored); document new variables in `server/.env.example`.

## Authentication

Better Auth with email/password and database sessions (see the `better-auth-best-practices` skill).

- `server/src/auth.ts`: the `auth` instance, using the Prisma adapter (PostgreSQL). Public sign-up is disabled (`disableSignUp: true`); users are created only on the server (seed script now, admin user-management API later). `role` is an extra user field (`'admin' | 'agent'`, default `agent`, `input: false` so clients can't set it). `trustedOrigins` comes from `TRUSTED_ORIGINS`.
- Tables `User`, `Session`, `Account` (password hash, `providerId: 'credential'`) and `Verification` are in `server/prisma/schema.prisma`.
- `server/src/app.ts` mounts `app.all('/api/auth/*splat', toNodeHandler(auth))` **before** `express.json()` (Better Auth parses its own bodies).
- Protect routes with `requireAuth` from `server/src/middleware/auth.ts`. It calls `auth.api.getSession({ headers: fromNodeHeaders(req.headers) })`, responds 401 `{ error: 'Unauthorized' }` when there is no session, and otherwise sets `res.locals.user` / `res.locals.session` (type `AuthSession`). Admin-only routes also use `requireAdmin` (after `requireAuth`), which responds 403 `{ error: 'Forbidden' }` for non-admins. `GET /api/me` returns the current user and session.
- User management lives in `server/src/routes/users.ts` (`usersRouter`, mounted at `/api/users`), which applies `requireAuth` + `requireAdmin` to every route. `GET /api/users` returns `UsersResponse` (from `@helpdesk/shared`) and selects only safe fields. `POST /api/users` creates an agent: it validates the body with `createUserSchema` from `@helpdesk/shared` (the client form uses the same schema; 400 `{ error, fields }` on failure, 409 for a duplicate email) and creates the user and credential account through `auth.$context.internalAdapter`, as the seed script does. `PATCH /api/users/:id` edits a user's name and email with `updateUserSchema` (same rules; the password is optional and a blank one keeps the current password; the role can't be changed), returning 404 for an unknown id and 409 when the email belongs to someone else. On the Users page, `UserFormDialog` is the form for both: without a `user` prop it renders the "New user" button, and with one it renders the pencil "Edit <email>" button in that user's row and opens the form filled with their data. `DELETE /api/users/:id` soft-deletes a user (204): it sets `User.deletedAt` and deletes their sessions in one transaction, so they're signed out everywhere; it returns 404 for an unknown or already deleted id and 403 when admins try to delete themselves. Deleted users are hidden from `GET /api/users`, give 404 on `PATCH`, and keep their row, so their email stays taken (409 on create). A `databaseHooks.session.create.before` hook in `auth.ts` refuses new sessions for them with the same 401 as a wrong password. Filter `deletedAt: null` in any new user query. `DeleteUserButton` is the trash icon next to the pencil: it asks for confirmation in an `AlertDialog` and is disabled on the signed-in admin's own row.
- Initial admin: `npm run db:seed -w server` creates it from `ADMIN_EMAIL` / `ADMIN_PASSWORD` / `ADMIN_NAME`, and skips it if it already exists.
- Env vars (in `server/.env.example`): `BETTER_AUTH_SECRET` (≥32 random chars, e.g. `openssl rand -base64 32`), `BETTER_AUTH_URL` (server URL), `TRUSTED_ORIGINS` (comma-separated client origins, e.g. `http://localhost:5173`).
- Client: `client/src/lib/auth-client.ts` exports `authClient = createAuthClient()` from `better-auth/react` with no `baseURL`, so requests go same-origin to `/api/auth` through the Vite proxy and the cookie stays first-party. Use `authClient.useSession()`, `authClient.signIn.email({ email, password })` and `authClient.signOut()`.
- Client routing (`client/src/App.tsx`): `/login` is public (`LoginPage` redirects to `/` if already signed in), and everything else is wrapped in `RequireAuth` (shows loading while the session is pending, otherwise redirects to `/login`) and `AppLayout` (header with user name and Sign out; admins also get a Users link). The "Helpdesk" title in `AppHeader` links to `/`. Admin-only pages (e.g. `/users`, the user table) are also nested in `RequireAdmin`, which sends non-admins to `/`; this is UI-only, so admin API routes must still check the role server-side. `authClient` uses `inferAdditionalFields` so `session.user.role` is typed.
- Sign-in failures return 401 `{ message: 'Invalid email or password', code: 'INVALID_EMAIL_OR_PASSWORD' }`; the login page shows `error.message`.

## Inbound email (tickets)

- No email provider is chosen yet. `POST /api/inbound/email` (`server/src/routes/inbound.ts`) takes one email in our own JSON format, `inboundEmailSchema` from `@helpdesk/shared` (`from { email, name? }`, `subject`, `text` and/or `html`, `messageId`, `inReplyTo?`, `references?`, `headers?`). A future provider adapter or mailbox poller translates its payload into this shape and calls the endpoint (or `receiveInboundEmail` directly).
- Auth is a shared secret, not a session: `Authorization: Bearer <INBOUND_EMAIL_SECRET>`, compared in constant time. 401 on a mismatch; 503 when the variable is unset (endpoint disabled). The router is mounted **before** `express.json()` with its own 5 MB parser.
- `receiveInboundEmail` (`server/src/inbound-email.ts`): auto-replies and bounces (`Auto-Submitted`, `Precedence`, `X-Autoreply`, mailer-daemon/postmaster) → `ignored`; a known Message-ID → `duplicate`; a reply whose `In-Reply-To`/`References` matches a message on a non-closed ticket from the **same sender** → `appended` (a resolved ticket reopens); anything else → `created` (new `Ticket` + first inbound `Message`). 201 for `created`, 200 otherwise, so senders don't retry. HTML-only emails are stored as plain text (`htmlToText`).
- `Ticket` / `Message` are in `server/prisma/schema.prisma`; `Message.emailMessageId` (unique, no angle brackets) dedups and threads. Ticket enums mirror `TICKET_STATUSES` / `TICKET_CATEGORIES` in `@helpdesk/shared`; the category defaults to `general_question` until AI classification exists.
- Try it locally (with `INBOUND_EMAIL_SECRET` in `server/.env`):
  `curl -X POST localhost:3000/api/inbound/email -H "Authorization: Bearer $SECRET" -H "Content-Type: application/json" -d '{"from":{"email":"student@example.com"},"subject":"Help","text":"Hi","messageId":"<a1@example.com>"}'`
- E2E: `e2e/inbound-email.spec.ts`; `serverEnv` sets `INBOUND_EMAIL_SECRET` from `.env.test` or a fixed fallback (`inboundEmailSecret()` in `e2e/test-env.ts`). It uses no sign-ins.

## Tickets page

- `GET /api/tickets` (`server/src/routes/tickets.ts`, `requireAuth`; admins and agents) returns `TicketsResponse` (`tickets`, `total`, `page`, `pageSize`). Query parsing uses `ticketListQuerySchema` from `@helpdesk/shared`: `status`, `category`, `q` (case-insensitive match on subject, requester email or name), `sort` (`TICKET_SORT_FIELDS`, the table's column ids: `subject`, `requester` (name, then email), `status`/`category` (enum order), `assignee` (name; unassigned last ascending), `createdAt`, `updatedAt`; `ticketOrderBy` in the router adds newest-first and id tiebreakers), `order`, `page`, `pageSize` (10/20/50). Invalid values fall back to the defaults (newest 20) instead of a 400, because they come from the URL.
- `/tickets` (`client/src/pages/TicketsPage.tsx`, linked as "Tickets" in the header for everyone) uses TanStack Table **v9** (`useTable` + `tableFeatures({ rowSortingFeature, rowPaginationFeature })`, `table.FlexRender`; v8's `useReactTable`/`getCoreRowModel` don't exist) with `manualSorting`/`manualPagination`. All list state lives in the URL search params (default values omitted), so filtering or searching resets to page 1 and links are shareable. The search box is debounced by 300 ms. Labels for statuses and categories are in `client/src/lib/tickets.ts`.
- Ticket detail: `GET /api/tickets/:id` returns `TicketResponse` (`TicketDetail`: the ticket plus `messages`, oldest first; 404 for an unknown id). `PATCH /api/tickets/:id` takes `updateTicketSchema` (any of `status`, `category`, `assigneeId`; `null` unassigns; an empty body is a 400) and returns the updated ticket. An `assigneeId` must be a user who isn't soft-deleted (else 400 `fields.assigneeId`). `GET /api/tickets/assignees` lists those users for every signed-in user (`GET /api/users` is admin-only); it's declared before `/:id`.
- Replies: `POST /api/tickets/:id/replies` takes `createReplySchema` (`body`, trimmed, 1–50,000 chars; `resolve`, default false; the reply form uses the same schema), adds an outbound `Message` from the signed-in user (`fromEmail`/`fromName` = their email/name), bumps the ticket's `updatedAt`, sets status `resolved` when `resolve` is true (same write; the form's "Send & resolve" button, hidden on resolved tickets) and returns 201 `TicketResponse`. 404 for an unknown id; 409 on a closed ticket (a student's answer to one would start a new ticket). Nothing is emailed yet: sending via a pg-boss job comes with the email provider.
- `/tickets/:id` (`client/src/pages/TicketDetailPage.tsx`): message thread with a reply form under it (replaced by "Reopen it to reply" on closed tickets) (bodies rendered as plain text with `whitespace-pre-wrap`, never as HTML) and a Details card where status, category and assignee save on change, plus "Assign to me". On success it writes the response into the `['ticket', id]` query and invalidates `['tickets']`. List links pass `state={{ listSearch }}` so "Back to tickets" restores the list's filters.
- `client/src/test/setup.ts` polyfills `hasPointerCapture`, `releasePointerCapture` and `scrollIntoView`, which Radix Select needs in jsdom.
- E2E: `e2e/tickets.spec.ts` creates tickets through the inbound email endpoint and uses a unique word in subjects/emails to search, so other tests' tickets don't interfere.

## Client UI

- Style only with Tailwind v4 utility classes; no custom CSS files or inline `style` props.
- `client/src/index.css` holds the Tailwind import and the default shadcn/ui theme (neutral base color, light/dark CSS variables, Geist font). Keep it: the theme tokens (`bg-primary`, `text-muted-foreground`, `text-destructive`, …) depend on it.
- Use shadcn/ui components from `@/components/ui` (style `radix-nova`, see `client/components.json`); add new ones with `npx shadcn@latest add <component>` from `client/`. Icons come from `lucide-react`.
- Fetch API data with TanStack Query (`useQuery`; the `QueryClientProvider` is in `client/src/main.tsx`) and `apiGet<T>(path)` from `client/src/lib/api.ts`, which throws with the server's `error` message on non-2xx responses.
- Forms use `react-hook-form` with a Zod (v4) schema via `zodResolver`: show each field's error below it (`aria-invalid` + `role="alert"`), and show server errors with `setError('root.serverError', …)`.
- Login form validation checks only that email is valid and password is non-empty; no client-side password length rule.

## Domain rules

- Ticket statuses: `open`, `resolved`, `closed`.
- Ticket categories (exactly one per ticket): `general_question`, `technical_question`, `refund_request`.
- Roles: `admin`, `agent`. The initial admin is seeded at deploy; only admins manage users.
- Authentication uses database sessions (session rows in Postgres, opaque ID in an httpOnly cookie), not JWTs.
- AI replies are drafts that an agent approves; the manual workflow must keep working if the AI provider fails.
